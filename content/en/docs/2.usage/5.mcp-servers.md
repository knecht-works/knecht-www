The agent can use the tools of remote [MCP servers](https://modelcontextprotocol.io/docs/getting-started/intro), for example to read a stack trace from Sentry or a spec from Notion. It decides itself when to call them, like any other tool.

![The MCP servers list in the agent settings of a project with two project servers and a global server, and the ready-made servers below it](/assets/knecht-mcp-servers-project.png)

## Where They Apply

Servers are set up in two places:

- **Settings > Agent:** the server applies to every project.
- **The project's agent settings:** the server applies to this project only. A project server with the same name as a global one replaces it in this project.

In a project, the list also shows the global servers. Their switch turns one off for this project only; the arrow leads to the global settings to edit it. Only owners add, edit, and remove servers.

## Adding a Server

"Add custom server" takes any remote server by its URL. Below it, ready-made servers for Sentry, Context7, Notion, and Cloudflare already know their URL and sign-in. Knecht only offers servers that the vendor runs itself.

The name is how the agent sees the server's tools: up to 32 lowercase letters, digits, and dashes, starting with a letter. "Test connection" in a server's menu checks that it answers and lists its tools.

## Authentication

The dialog's "Authentication" field picks how Knecht signs in:

| Method | Use it for |
| --- | --- |
| None | Public servers, for example Context7 with lower rate limits. |
| Token | A ready-made server with an API key or token from the vendor. |
| Headers | A custom server that expects its own headers, for example an API key. |
| OAuth | Signing in with the vendor's account in the browser. |

A ready-made server offers the methods its vendor supports, a custom server None, Headers, and OAuth.

With OAuth, "Connect" registers Knecht with the server and opens its sign-in. The row then shows who connected it and when, and the agent works with the rights of that account. Knecht refreshes the access token before it expires. When the refresh fails, the row shows the reason and "Reconnect". A working connection keeps working until a reconnect is finished.

Some servers do not let clients register themselves. For those, turn on "Use my own OAuth client", create a client at the vendor with the shown "Redirect URL", and enter its client ID and secret.

::note
The sign-in redirects back to the dashboard. Many vendors only accept HTTPS or localhost as a redirect address, so an instance on another plain HTTP address is better connected with a token.
::

Tokens, header values, and OAuth credentials are stored encrypted and only shown as a preview after saving. The agent gets them as environment variables, never written into its config file.

## When a Server Fails

Knecht checks every server before each AI step. A server that does not answer, or whose sign-in expired, is left out of that step, and the run's transcript gets a notice with the reason. The step runs without that server's tools instead of failing.
