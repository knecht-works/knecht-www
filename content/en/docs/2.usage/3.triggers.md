---
title: Triggers
description: Start workflows from GitHub events, Jira tickets, or a schedule.
---

A trigger starts a workflow without anyone pressing "Run". It sits at the head of the workflow in the editor, targets one or more projects, and starts a separate run per project each time it fires. A workflow can have any number of triggers, also several of the same kind.

## Shared Behavior

- **Automation switch.** The switch in the editor header turns all triggers of a workflow on or off. Each trigger also has its own toggle. Manual runs and tests are not affected by either.
- **Last complete version.** Triggers run the last version of the workflow that passed validation. An incomplete edit stays a draft and the previous complete version keeps running. Automation cannot be switched on before the workflow is complete once.
- **One run per project.** A trigger lists the projects it applies to and starts one run per project. GitHub events only run on the project of the repository that sent them.
- **Sessions.** Runs on a GitHub issue or pull request join the [session](/docs/get-started/concepts#sessions) of that issue, so two triggers firing on the same issue run one after the other, never in parallel. Push, Jira, and scheduled runs each get a fresh session that closes after the run.
- **Inputs.** Every trigger delivers the same run variables, `{{ inputs.identifier }}`, `{{ inputs.title }}`, `{{ inputs.body }}`, `{{ inputs.url }}`, and `{{ inputs.event }}`. What they hold depends on the trigger and is listed below. A field the event does not have arrives as an empty string.

## Manual

Every workflow can be started by hand, from the project page or from "Run" in the editor, without any trigger. A manual trigger can still be saved to mark a workflow as manual-only and to keep its projects in one place. Manual runs use the current draft, and the run popover accepts mock inputs, see [Testing before You Activate](/docs/usage/workflows#testing-before-you-activate).

## GitHub

GitHub events arrive through the webhook of the GitHub App from [Setup](/docs/get-started/setup). There is nothing to configure per repository. The webhook has to reach the instance, so GitHub triggers do not work on a local install without a public address.

### Events

A GitHub trigger listens to one event.

| Event | Fires on | Inputs |
| --- | --- | --- |
| Push | A push to a branch. Tag pushes and branch deletions are ignored. | `identifier` is the short commit hash, `title` the commit message, `url` the commit link. `body` is empty. The run checks out the pushed branch. |
| Pull request | A pull request being opened, reopened, or receiving new commits. | `identifier` is the pull request number, plus its title, body, and link. The run checks out the pull request's branch. |
| Issue | A new issue, a label being added, or both. | `identifier` is the issue number, plus its title, body, and link. The run uses the default branch. |

Comments that mention `@knecht-works` are not a trigger. They are follow-ups in the issue's session, see [Follow-Ups and Mentions](/docs/usage/agent#follow-ups-and-mentions).

### Branch Filter

Push and pull request triggers take a comma-separated list of branch names. For a push it is the pushed branch, for a pull request the base branch. Names are matched exactly, wildcards are not supported. An empty filter matches every branch.

### Issue Label

When the trigger reacts to a label, the label name is required and matched exactly. Combined with "opened", the trigger fires on new issues and on the label, whichever happens.

## Jira

Jira triggers need the connection from [Setup](/docs/get-started/setup#jira-optional). The trigger watches one Jira project for exactly one condition.

### Conditions

- **Label.** A label is added to a ticket. The default is `knecht`.
- **Status.** A ticket reaches a status. The list shows the statuses of the project's board.
- **Assignee.** A ticket is assigned to the Knecht account behind the connection.

### Matching

Knecht checks Jira about every 45 seconds and compares the matching tickets with the last check. Tickets that already match when the trigger is created or edited are ignored. A ticket that stops matching and matches again later fires again.

### Inputs

`identifier` is the ticket key, for example `PROJ-123`, `title` the summary, `body` the description as Markdown, and `url` the ticket link. Runs use the default branch. When a run opens a pull request, Knecht posts the link as a comment on the ticket.

## Cron

A cron trigger fires on a schedule in standard five-field cron syntax, minute, hour, day of month, month, day of week. The form offers presets from every 15 minutes to weekly, for example every Monday at 09:00 for a dependency update run.

### Presets

| Preset | Expression |
| --- | --- |
| Every 15 minutes | `*/15 * * * *` |
| Hourly | `0 * * * *` |
| Daily at 09:00 | `0 9 * * *` |
| Weekdays at 09:00 | `0 9 * * 1-5` |
| Weekly on Monday at 09:00 | `0 9 * * 1` |

### Syntax

Times are in the server's local time. Supported are `*`, steps like `*/15`, ranges like `1-5`, and lists like `1,15`. Seconds and aliases like `@daily` are not supported. [crontab.guru](https://crontab.guru) explains the format and translates an expression into plain words. If the instance was down when a slot passed, the schedule fires once after the restart, not once per missed slot.

::warning
A scheduled run has no issue behind it and delivers no inputs. Each run gets a session of its own that closes when the run is finished.
::
