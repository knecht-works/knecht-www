---
title: Triggers
description: Start workflows from GitHub events, Jira tickets, or a schedule.
---

A trigger starts a workflow without anyone pressing "Run". It sits at the head of the workflow in the editor, targets one or more projects, and starts a run each time it fires. A workflow can have any number of triggers, also several of the same kind. Starting a workflow by hand needs no trigger, see [Testing before You Activate](/docs/usage/workflows#testing-before-you-activate).

## Trigger Types

| Type | Starts a run when | Details |
| --- | --- | --- |
| Schedule | A cron expression is due, for example every Monday at 09:00. | [Schedule](#schedule) below |
| GitHub | Something happens on a pull request or an issue: opened, ready for review, new commits, a label, an assignment. | [GitHub](/docs/integrations/github#triggers) |
| Jira | Something happens on a ticket: created, assigned to Knecht, a label, a status. | [Jira](/docs/integrations/jira#triggers) |

GitHub works on every instance, Jira has to be [connected](/docs/integrations/jira#setup) first. Both arrive through webhooks, so they need an instance that is reachable from the internet.

## Adding a Trigger

"Add trigger" at the head of the workflow opens the dialog. Pick the source, one or more projects, and what the source should react to. For Jira, only projects linked to a Jira project are listed.

![The trigger dialog with the three sources Schedule, GitHub, and Jira, the project field with two projects as chips, and the GitHub form with its events and filters below](/assets/knecht-trigger-github.png)

Once saved, the trigger appears at the head of the workflow with a one-line summary, for example "On pull request · opened, ready for review · base main". The edit button on that row opens the dialog again.

### Events and Filters

GitHub and Jira triggers share one form with two sections.

- **Fires when.** The events. Any ticked event fires the trigger. Some take a value, such as the label name of "Label added".
- **Only when.** The filters, added with "Add filter". Every filter has to match. Several comma-separated values match when one of them fits, and `*` stands for any text, as in `releases/*`.

Events are joined by "or", filters by "and". A trigger with the events "Opened" and "Label added" and the filters "Base branch matches `main`" and "Author is not `renovate[bot]`" fires on either event, but only for pull requests against `main` that the bot did not open. Which events and filters exist is listed on the [GitHub](/docs/integrations/github#triggers) and [Jira](/docs/integrations/jira#triggers) pages.

## How Triggers Behave

- **Automation switch.** The switch in the editor header turns all triggers of a workflow on or off. Each trigger also has its own toggle. Manual runs are not affected by either.
- **Last complete version.** Triggers run the last version of the workflow that passed validation. An incomplete edit stays a draft and the previous complete version keeps running.
- **One run per project.** A schedule starts one run for every project of the trigger. GitHub and Jira events only run on the project whose repository or linked Jira project sent them.
- **Sessions.** Runs on a GitHub issue or pull request or on a Jira ticket join its [session](/docs/get-started/concepts#sessions), so two triggers firing on the same issue run one after the other. Scheduled and manual runs get a session of their own that closes after the run.
- **Inputs.** GitHub and Jira triggers fill the run variables `{{ inputs.identifier }}`, `{{ inputs.title }}`, `{{ inputs.body }}`, `{{ inputs.url }}`, `{{ inputs.event }}`, `{{ inputs.status }}`, `{{ inputs.labels }}`, `{{ inputs.assignee }}`, and `{{ inputs.author }}`. A field the event does not have arrives as an empty string. A schedule delivers no inputs.

## Schedule

A schedule fires on a standard five-field cron expression: minute, hour, day of month, month, day of week. The form offers presets from every 15 minutes to weekly on Monday at 09:00.

![The trigger dialog with Schedule selected as source, two projects as chips, the cron expression for every 15 minutes, and the presets below the field](/assets/knecht-trigger-schedule.png)

Times are in the server's local time. Supported are `*`, steps like `*/15`, ranges like `1-5`, and lists like `1,15`. Seconds and aliases like `@daily` are not supported. [crontab.guru](https://crontab.guru) explains the format and translates an expression into plain words. If the instance was down when a slot passed, the schedule fires once after the restart, not once per missed slot.
