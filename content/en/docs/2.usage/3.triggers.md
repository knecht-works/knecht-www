title: Triggers
description: Start workflows from GitHub events, from an issue tracker, or on a schedule.

A trigger starts a workflow without anyone pressing "Run". It sits at the head of the workflow in the editor, targets one or more projects, and starts a run each time it fires. A workflow can have any number of triggers, also several of the same kind. Starting a workflow by hand needs no trigger, see [Testing before You Activate](/docs/usage/workflows#testing-before-you-activate).

## Trigger Types

| Type | Starts a run when | Details |
| --- | --- | --- |
| Schedule | A cron expression is due, for example every Monday at 09:00. | [Schedule](#schedule) below |
| GitHub | Something happens on a pull request or an issue: opened, ready for review, new commits, a label, an assignment. | [GitHub](/docs/integrations/github#triggers) |
| Jira | Something happens on a ticket: created, assigned to Knecht, a label, a status. | [Jira](/docs/integrations/jira#triggers) |
| Plane | Something happens on a work item: created, assigned to Knecht, a label, a state. | [Plane](/docs/integrations/plane#triggers) |
| Linear | Something happens on an issue: created, assigned to Knecht, a label, a status. | [Linear](/docs/integrations/linear#triggers) |

This table is the list of sources. Each one has its own page with its events, filters, and setup, and everything on this page applies to all of them.

GitHub works on every instance. An issue tracker has to be connected first, the Setup section of its page walks through it. Until then, the dialog shows a hint with the way to Settings, Integrations instead of the form. All sources except the schedule arrive through webhooks, so they need an instance that is reachable from the internet.

## Adding a Trigger

"Add trigger" at the head of the workflow opens the dialog. Pick the source, one or more projects, and what the source should react to. For an issue tracker, only projects that are linked to their counterpart in the tool are listed. The link is set in the project settings.

![The trigger dialog with the sources in a row at the top, the project field, and the Linear form with its events and filters below](/assets/knecht-trigger-linear.png)

Once saved, the trigger appears at the head of the workflow with a one-line summary, for example "On pull request · opened, ready for review · base main". The edit button on that row opens the dialog again.

### Events and Filters

All triggers except the schedule share one form with two sections.

- **Fires when.** The events. Any ticked event fires the trigger. Some take a value, such as the label of "Label added".
- **Only when.** The filters, added with "Add filter". Every filter has to match. A filter takes several values and matches when one of them fits.

Events are joined by "or", filters by "and". A trigger with the events "Opened" and "Label added" and the filters "Base branch matches `main`" and "Author is not `renovate[bot]`" fires on either event, but only for pull requests against `main` that the bot did not open. Which events and filters a source has is listed on its page, see [Trigger Types](#trigger-types).

### Matching

The values of events and filters follow the same rules in every source.

- **Picked from the tool.** Labels, branches, issue types, priorities, and states are offered from the values that exist in the tool, read live. Logins are typed.
- **Patterns.** A filter also takes a typed pattern. `*` stands for any text: `releases/*` matches `releases/v1`, `team-*` every label with that prefix, and `*[bot]` every bot account. Without a `*` the value has to match as a whole.
- **Upper and lower case count.** `Bug` does not match `bug`. This holds for every filter, logins included, and for the label of "Label added".
- **Event values are no patterns.** The label of "Label added" is matched exactly. A typed name is accepted, but the form warns that nothing fires the trigger until that label exists.

### Issue Trackers

Issue trackers share the events "Created", "Assigned to Knecht", "Label added", and an event for a status being reached. An issue that is created with the label, in the status, or already assigned to Knecht fires as well, without "Created" being ticked.

The status list of that event has two groups.

- **Category.** An entry such as "Any Done" stands for a whole status category of the tool, whatever the single statuses are called. The trigger fires when an issue crosses into the category. A move inside it, for example from "In Progress" to "In Review", does not fire.
- **Exact status.** The statuses of the selected projects, read live from the tool. The trigger fires every time an issue moves into that status.

With several projects selected, the exact statuses are split into the ones all projects share and "Only in some", with the keys of their counterparts in the tool. If the picked status is missing in one of them, the form warns that nothing there will ever fire the trigger. Pick a category, a status all projects share, or create a second trigger.

## How Triggers Behave

- **Automation switch.** The switch in the editor header turns all triggers of a workflow on or off. Each trigger also has its own toggle. Manual runs are not affected by either.
- **Last complete version.** Triggers run the last version of the workflow that passed validation. An incomplete edit stays a draft and the previous complete version keeps running.
- **One run per project.** A schedule starts one run for every project of the trigger. Every other event only runs on the project whose repository or linked counterpart in the issue tracker sent it.
- **Sessions.** Runs on a GitHub issue or pull request or on an issue of an issue tracker join its [session](/docs/get-started/concepts#sessions), so two triggers firing on the same issue run one after the other. Scheduled and manual runs get a session of their own that closes after the run.
- **Inputs.** All triggers except the schedule fill the run variables `{{ inputs.identifier }}`, `{{ inputs.title }}`, `{{ inputs.body }}`, `{{ inputs.url }}`, `{{ inputs.event }}`, `{{ inputs.status }}`, `{{ inputs.labels }}`, `{{ inputs.assignee }}`, and `{{ inputs.author }}`. A field the event does not have arrives as an empty string. A schedule delivers no inputs.

## Schedule

A schedule fires on a standard five-field cron expression: minute, hour, day of month, month, day of week. The form offers presets from every 15 minutes to weekly on Monday at 09:00.

![The trigger dialog with Schedule selected as source, two projects as chips, the cron expression for every 15 minutes, and the presets below the field](/assets/knecht-trigger-schedule.png)

Times are in the server's local time. Supported are `*`, steps like `*/15`, ranges like `1-5`, and lists like `1,15`. Seconds and aliases like `@daily` are not supported. [crontab.guru](https://crontab.guru) explains the format and translates an expression into plain words. If the instance was down when a slot passed, the schedule fires once after the restart, not once per missed slot.
